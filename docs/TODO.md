# TODO: the 3D, tactical, trading overhaul

The ticket list for turning the ASCII roguelike into an isometric 3D game with
squad tactics and a town that grows from trade. The game design lives in
[design.md](design.md). [ROADMAP.md](ROADMAP.md) keeps the older backlog.

## How to work a ticket

- The coordinator (the main Claude session) hands out tickets and is the only
  one who edits the `Status` fields in this file. Agents do not edit this file.
- One ticket, one agent, one git worktree, one branch named `ticket/<ID>`.
- Only take a ticket whose `Needs` are all `done`.
- Read `CLAUDE.md` first. UK English. Zero compiler and clippy warnings.
  Keep "Toolbox:" dead code. Commit as one line, `feat: add ...`.
- A ticket is done when every `Done when` line is true and you ran the check
  yourself. Pure logic gets a unit test. Anything visible gets a scene in
  `tools/scenes.json` and a look at the contact sheet.
- Work in batches (see "Verifying changes" in `CLAUDE.md`): all the code and
  unit tests first, then one `tools/scenes.py` run, read the table and logs,
  look at the sheet once, fix everything, repeat. Do not launch the game after
  each small change. Run the whole suite once before reporting.
- Never leave a game, a loop or a build running in the background.
- Art tickets (`A..`) drive the one live Blender instance, so only one art
  ticket runs at a time.
- Report back what you changed, what you verified and how, and what you did not
  verify.

Status values: `todo`, `in progress`, `done`, `blocked`.

## Decisions already made

Product calls (from the owner, November 2026):

1. True 3D. Bevy PBR meshes, an orthographic isometric camera, real lights and
   shadows. Not pre-rendered sprites.
2. Combat is XCOM-like with a controllable party: action points, hit chances,
   cover, overwatch. Only the fighting borrows from XCOM.
3. Outside combat the party moves freely by click. The game drops into turn
   mode when hostiles and the party become aware of each other.
4. The town persists across permadeath. Every run, win or lose, advances it.
5. Assets are stylised low-poly models made in Blender by us.
6. The in-game ASCII renderer is deleted once 3D reaches parity. WASM is
   dropped if 3D lighting struggles there. The map generation visualiser stays
   2D and keeps using `spawn_map_tiles` in `map_render.rs`.
7. Point and click to move. WASD pans the camera. HJKL, arrows and numpad
   movement are removed.

Technical conventions (so parallel tickets agree):

- `Position` (grid x, y) stays the gameplay truth. Rendering maps grid `(x, y)`
  to world `(x, 0, y)`. One tile is one world unit, one metre, one Blender unit.
- Models are glTF binary in `assets/models/<name>.glb`. Blender sources live in
  `art/`. Model origin is the tile centre at floor height. Walls are 2 m tall.
- Raws entries gain a `model` field beside `glyph`. A missing model falls back
  to a coloured primitive, so code tickets never wait on art.
- Gameplay rules are pure functions over plain data (hit chance, cover, move
  range, prices, town simulation), separate from Bevy systems, with unit tests.
- Town state is its own file, `town.json`, separate from `savegame.json`, and
  is never deleted by permadeath.

Assumed defaults (the owner can overrule; change the ticket if so):

- Party size is 4. The run ends when every member is dead.
- 2 action points per unit per round.
- Characters animate by code tweens (slide, hop, lunge) at first. Skeletal
  animation is a late ticket (A09).
- Hunger stays per party member.
- A Town Portal scroll and the up stairs return the party to town. Coming back
  to the dungeon regenerates the level at the deepest depth reached.

Direction from the owner's first playtest (15 November 2026):

- The game should feel smooth and polished, not grid-bound. The old grid-based
  feel is not something to preserve, and `docs/design.md` is a guideline that
  will change. Where a ticket has a choice, pick the smoother presentation:
  continuous camera motion, units that glide, eased transitions.
- Settled by the owner: this is presentation only. Tiles stay the rules
  underneath (as in XCOM); nothing the player sees or feels should snap.

Settled questions (owner, 15 November 2026):

1. Depth numbering. The town is depth 0 and the dungeon runs from depth 1 to
   12, matching the design table. E07 makes the change (the code today has the
   town at depth 1), including the harness `--depth` meaning, the HUD, saves
   and `CLAUDE.md`.
2. The Heart blocks Town Portals. A party carrying it must climb out. E07.
3. Status effects under action points. Poison deals its damage at the start of
   the unit's turn. A confused unit's move goes to a random adjacent tile and
   still costs its AP. C03.
4. Using an item costs 1 AP. C03.

### F10 Performance pass
- Status: todo

## C: Tactical combat (XCOM style, with a party)

### C01 Party model
- Status: done
- Needs: F05
- Replace the single `Player` assumption. A `PartyMember` component, an
  `ActiveUnit` resource, a party of 4 spawned at new game, and a click or Tab
  to select a unit. Vision is the union of all members' viewsheds. Inventory,
  equipment, hunger and HUD work per member. Game over when all are dead.
  Migrate every `With<Player>` query in one wave. Do not keep a compatibility
  alias.
- Files: `src/player.rs`, `src/levels.rs`, `src/viewshed.rs`,
  `src/inventory.rs`, `src/ui/hud.rs`, `src/monsters.rs`.
- Done when: four heroes can each be selected and moved, monsters target the
  nearest one, and the run ends only when the last one dies.

### C02 Explore mode and combat mode
- Status: done
- Needs: C01
- Redesign `RunState` in `game_flow.rs` as an explicit state machine with two
  top-level modes. Explore: a click moves the whole party, followers pathing
  behind the leader, time advancing per step. Combat: starts when a hostile
  and a party member see each other, alternates a party phase and an enemy
  phase, and ends when no aware hostile remains.
- Done when: unit tests cover the mode transitions, and in game the party
  walks freely, drops into combat on contact and returns to explore after.

### C03 Action points and movement range
- Status: done
- Needs: C02
- Each unit has 2 action points per round and a `movement` stat. Actions:
  move (1 AP), dash (2 AP), attack (ends the unit's turn), use item (1 AP),
  end turn. Poison deals its damage at the start of the unit's turn. A
  confused unit's move goes to a random adjacent tile and still costs its AP.
  Units act in any order within the party phase. Move range comes from a pure
  flood fill over `Map::get_available_exits` and is drawn as a one-AP zone and
  a two-AP zone. Monsters spend AP by the same rules.
- Done when: unit tests cover range and AP spending, and the range overlay
  matches where a unit can go.

### C04 Hit chance, ranged attacks and criticals
- Status: done
- Needs: C03
- Replace the deterministic melee in `combat.rs`. A pure `hit_chance`
  function from attacker aim, target defence, range, cover and height.
  Weapons in the raws gain damage range, range bands and crit chance. Line of
  sight uses the existing Bresenham code. Rolls go through `GameRng`.
- Done when: a table-driven unit test pins the hit chance for at least ten
  cases, and bows and spells work on the same rules.

### C05 Cover and flanking
- Status: done
- Needs: C04
- Walls and tall props give full cover, low props half cover, per direction.
  Props get a `cover` value in the raws. A flanked target gets no cover and
  takes a crit bonus. Cover shields show on the hovered destination tile.
- Done when: unit tests cover directional cover and flanking, and the hover
  indicator agrees with them.

### C06 Overwatch and hunker down
- Status: done
- Needs: C04
- Overwatch spends the turn and fires at the first hostile that moves in view
  during the enemy phase, with an aim penalty. Hunker down doubles cover until
  the next turn. Enemies can use both.
- Done when: unit tests cover the reaction trigger, and it works in game for
  both sides.

### C07 Tactical enemy AI

- Needs: C05, C06
- Monsters wait in groups until alerted. Once active they score candidate

- Files: `src/monsters.rs`, `raws/spawns.json`.
- Done when: unit tests pin the tile scoring, and in play ranged monsters
